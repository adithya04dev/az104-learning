Identity lifecycle · Guided lab

Onboard the Pulse product squad.

Create a clean identity model for an employee and an agency partner, then test a group-scoped SSPR rollout. The lab emphasizes evidence and safe administration.

30–45 minutesPortal-firstNo paid Azure resource deployment
Before changing anything
Use a personal lab tenant or an explicitly approved work sandbox. Never create test identities in a production tenant without authorization. Do not place passwords in CLI arguments, screenshots, notes, or chat. SSPR testing normally needs Entra ID P1 and suitable administrative roles.

Run the lab

1

Inventory your permissions and license

In the Microsoft Entra admin center, inspect your assigned directory role and tenant license. For the creation path, you generally need an appropriate user-management role; the official user guide identifies User Administrator for new users and Guest Inviter for external invitations. The SSPR tutorial requires at least Authentication Policy Administrator and Entra ID P1.

Predict: Which steps will your current identity permit? Write the answer before testing.

2

Create the product groups

Go to Entra ID → Groups → New group. In a sandbox, create security groups named az104-pulse-engineers and az104-sspr-pilot. Use assigned membership so the membership decision remains explicit.

Verify: Record each group's object ID and membership type. Explain why the object ID is more reliable than the display name for automation.

Observation mode: If you cannot create groups, open an existing non-sensitive group. Identify its type, membership type, owners, members, and object ID without editing it.
3

Create an internal test member

In Entra ID → Users → New user → Create new user, create a clearly labelled sandbox user such as az104-asha. Use the portal-generated temporary password and follow your organization's secure delivery process. Add the user to both lab groups.

Predict: Does group membership alone grant access to an Azure resource? Why?

Observation mode: Compare the properties of one existing internal member with the group membership list. Do not open or record personal attributes that are irrelevant to the lab.
4

Invite an external guest

Choose New user → Invite external user. Use an address you control or an approved lab address, label the invitation purpose, and add the guest to az104-pulse-engineers. Inspect the resulting user type and external identity information.

Verify: Compare Asha and Diego: where does each authenticate, what user type appears, and what access do they have before any Azure RBAC assignment?

Observation mode: Inspect a non-sensitive existing guest record and compare its user type and identities with an internal member. Make no changes.
5

Pilot SSPR

If licensed and authorized, go to Entra ID → Password reset → Properties, choose Selected, select az104-sspr-pilot, and save. Review the current Authentication methods policy and registration configuration. Test only with the non-admin lab user through an InPrivate window.

Predict: What happens if the user is in the group but has not registered an allowed verification method?

Verify: Capture only the outcome and error category—never credentials or security information.

Observation mode: Read the current SSPR scope and registration policy without changing it. Trace the exact prerequisites from the official tutorial and write which one blocks the active path.
6

Clean up deliberately

Remove the guest and lab member from the groups, delete only identities and groups you created, and confirm they no longer appear in active users/groups. In a real organization, offboarding may include retention, audit, access review, and delayed deletion; do not treat immediate deletion as a universal production process.

Explain: Why should disabling sign-in and removing authorization happen before or alongside deletion in a real incident?

Evidence gate

Do not mark this lab complete until you can explain all four:

  1. Internal member versus external guest.
  2. Why groups scale entitlement management.
  3. Why a license is not an Azure resource permission.
  4. Why SSPR scope and registered verification methods both matter.
Official procedures
  • Create and invite users
  • Enable and test SSPR
